# Handoff: PHP 8.5 / Symfony 8.1 upgrade — 2026-08-06

## Goal

Verify f43.me (and the graby/php-readability stack it depends on) actually run on
current PHP (8.5) and Symfony (8.1) bundles. That's it — this wasn't about shipping
f43.me as a live site. It isn't used much day-to-day; the point was to prove out the
upgrade path and fix whatever broke, since the same graby/php-readability stack is
what we want to reuse in the news project next.

**Result: done.** All 309 tests pass on PHP 8.5.9 / Symfony 8.1.2 / Postgres 18.

## What actually changed

**f43.me** (`tac-upgrade`, based on `main` — `main` already had your April 2026
"update to Symfony 8" commit, built cleanly on top of real upstream state; the old
`tac` branch had diverged from a much older point and never got that work):
- `php` `^8.4` → `^8.5`, Flex's `extra.symfony.require` → `^8.1`
- `DATABASE_URL` switched from a stale unused `mysql://` default to the shared dev
  Postgres (`postgresql://postgres:docker@127.0.0.1:5434/f43me`), per `CONVENTIONS.md`
- Dropped the MySQL-only `default_table_options` (charset/collate) from
  `doctrine.yaml` — dead weight now that Postgres is the real target
  (`identity_generation_preferences` was already configured for
  `PostgreSQLPlatform`, so Postgres was clearly the intended backend all along)
- `composer outdated --direct` is clean except `doctrine/dbal`, intentionally pinned
  to `4.5.x-dev` — that's the branch with the `Schema::edit()` API that
  `doctrine:schema:create`/`schema:update` need; nothing to fix there, just don't
  "helpfully" bump it to `5.0.x-dev`
- Dropped `composer/package-versions-deprecated` (abandoned, zero usage)
- JS assets current (`es-module-shims` bumped to 2.8.4; nothing else was stale)
- Cherry-picked your "add parser" commit from the old `tac` branch (the two
  scss/css commits from that branch were skipped — `main`'s own AssetMapper
  migration already supersedes them with a cleaner result)

**tacman/graby** (`tac`, merged `upstream/master` in — 64 commits):
- Picked up upstream's `ContentExtractor` → `ExtractedContent` refactor (returns a
  value object now instead of mutating instance state) and their `Monolog\Level`
  fix (the old array-offset access on a `LogRecord`/`Level` enum was a hard
  `TypeError` under Monolog 3)
- Re-applied the one real local fix on top: `\extension_loaded('tidy')` guards the
  tidy call in `ContentExtractor::process()`, so it degrades gracefully with or
  without the extension installed
- Kept the deliberate fork choice of depending on `tacman/php-readability` instead
  of `j0k3r/php-readability`
- Widened `symfony/options-resolver` to include `^8.0` (this was the actual thing
  blocking f43.me's first resolve attempt)
- 258 tests pass

**tacman/php-readability** (`tac`, merged `upstream/master` in — 51 commits, tagged
`2.1.0`):
- Fixed `'input-encoding' => '????'` in `$tidy_config` — a literal placeholder that
  was never filled in, silently never exercised because tidy usually wasn't
  installed/enabled. Now that it runs, this was a hard `TypeError` from
  `tidy_repair_string()`. Matches upstream's own value.
- Fixed a real regression: the constructor auto-called `init()` (added in a WIP
  commit — dangling empty `try/catch` blocks and a commented-out `dd()` call gave it
  away). Every real caller (graby, this repo's own tests) *also* calls `->init()`
  explicitly after construction, so `init()` ran twice — the second pass ran against
  an already-consumed DOM and silently overwrote good results with empty ones. This
  is why `testWithAside`, `testPreFilters`, and `testCharsetAfterTitle` were failing.
- 47 tests pass
- **README now documents the explicit-single-`init()`-call contract** — if news (or
  anything else) ends up using `Readability` directly rather than through graby,
  read that note first.

## Next session: news integration

You said the real plan is to integrate this stack with the news project, not run
f43.me itself. Worth knowing going in:

- `ContentExtractor::process()`'s return type changed (upstream's refactor, now in
  graby's `tac` branch) — it returns `ExtractedContent`, not the old
  mutate-then-read-properties pattern. If news's own code (or any code you write for
  it) calls into graby directly rather than through `Graby::fetchContent()`, that's
  the API to check first.
- `Graby::fetchContent()` itself (the actual public entry point most consumers use)
  already matched the new internals cleanly during the merge — no conflict there,
  so if news just calls `$graby->fetchContent($url)` today, this is a non-event.
- Tidy is fully optional now (both graby's and php-readability's `composer.json`
  have no `ext-tidy` requirement, and the code gracefully degrades either way) — one
  less thing to provision if news's environment doesn't have it.

## Someday: PWA

Noted for whenever this comes up again — the fetching (graby/readability content
extraction) needs to happen server-side, not in the PWA client. A PWA can't do
arbitrary cross-origin fetches of article HTML from the browser (CORS), and even if
it could, you wouldn't want tidy/DOM-parsing work running client-side. The shape is
probably: keep the extraction pipeline as a backend service (this is exactly what
f43.me/news already are), and the PWA is a thin client against that backend's API —
not a reason to restructure graby/readability themselves.
